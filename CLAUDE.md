# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Utility Optimizer CRM: a standalone CRM (not Odoo) for an Irish energy and Worldpay broker. It's an npm-workspaces monorepo:

- `packages/shared` (`@uo/shared`): pure domain code shared by both apps. It holds the enums, the 18-stage pipeline (`stages.ts`), the permission matrix (`permissions.ts`), stage-gate rules (`rules.ts`), MPRN/GPRN checks and Zod request schemas. It compiles to CommonJS in `dist/`; **rebuild it (`npm run build -w @uo/shared`) after any change**, because the API and web consume the build (Jest maps to `src` directly).
- `apps/api` (`@uo/api`): NestJS 11 + Prisma 6 + PostgreSQL + BullMQ/Redis + S3. The same code runs as the HTTP API (`dist/main.js`) and the background worker (`dist/worker.js`).
- `apps/web` (`@uo/web`): Next.js 15 App Router client. It calls only `/api/*`, which `next.config.ts` rewrites to the API (`API_ORIGIN`, default `http://127.0.0.1:4000`; fixed at build time).

## Commands

```bash
docker compose up -d                       # Postgres on 127.0.0.1:5433 (not 5432), Redis 6379, SeaweedFS S3 8333, Mailpit 8025
npm run build -w @uo/shared                # required before running/type-checking the apps
npm run db:migrate && npm run db:seed      # prisma migrate deploy + idempotent seed (demo users unless NODE_ENV=production)
npm run dev:api                            # nest start --watch on :4000 (Swagger at /api/docs)
npm run dev:web                            # next dev on :3000
npm run lint                               # eslint (flat config at root)
npm run typecheck
npm test                                   # shared + API unit + API integration (integration needs docker compose)
npm run test:e2e                           # Playwright + axe; needs API + web running and the dev seed loaded
npm run migrate:customers -w @uo/api -- <sheet.xlsx> [--commit]   # one-off import of existing customers (docs/migration.md); dry run without --commit
npm run migrate:documents -w @uo/api -- <pdf folder> [--commit]   # attaches their signed PDFs
```

Single tests:

```bash
cd packages/shared && npx jest -t "stage gates"
cd apps/api && npx jest --selectProjects unit -t "TOTP"
cd apps/api && npx jest --runInBand test/integration/opportunities.test.ts -t "activation"
cd apps/web && npx playwright test -g "duplicate customers"
```

Security tests: `test/integration/pentest.test.ts` attacks every route from the live OpenAPI document (anonymous, no CSRF token, second salesperson with the first one's ids, injection payloads, secret patterns in responses); a new route is covered automatically, and a new public route must be added to its `PUBLIC` list. `hardening.test.ts` holds regressions for the fixes in `docs/security-assessment.md`. Load test: start a built API on a test database, then `STRESS_DATABASE_URL=… STRESS_BASE_URL=… npm run stress -w @uo/api` (see the script header).

API integration tests boot the real `AppModule` against `TEST_DATABASE_URL` (the `uo_crm_test` database is created by `infra/postgres/init`). They truncate all tables per file, use local-disk storage and a `RecordingJobQueue` instead of Redis, and run with `--runInBand`. Set `TEST_LOG_ERRORS=1` to see server errors behind a 500. Local SeaweedFS needs `S3_SERVER_SIDE_ENCRYPTION=none` (it returns SSE objects still encrypted). Config comes from `apps/api/.env` (Node's built-in `.env` loading, no dotenv); blank values count as unset.

Schema changes: edit `apps/api/prisma/schema.prisma` and add a migration folder under `prisma/migrations/` (`npx prisma migrate dev` needs a running DB; offline, diff the committed schema against the edited one with `prisma migrate diff --from-schema-datamodel <HEAD copy> --to-schema-datamodel prisma/schema.prisma --script`; `--from-migrations` needs a shadow database). Constraints Prisma can't express live in `20261014000100_integrity/migration.sql`. Then regenerate the docs with `node scripts/gen-field-dictionary.js` (and `node scripts/gen-security-matrix.js` after permission changes).

## Architecture rules that span files

- **Permissions are enforced in the API, from one table.** `CAPABILITIES` in `packages/shared/src/permissions.ts` is the matrix. Route-level checks use `@RequireCapability`; row-level opportunity access goes through `OpportunityAccess` (`apps/api/src/opportunities/access.service.ts`: `readable` returns 404 for other people's deals, `writable` 403; `visibleWhere` for lists; `customerWhere`/`linkableCustomer` give salespeople only the customers they created or that sit on a deal they can see). Every service touching an opportunity's children (energy, merchant, documents, signatures, activities) calls `access.readable/writable` first. The web app only uses capabilities (from `/auth/me`) to hide buttons.
- **Global guard order** (`app.module.ts`): Throttler → `SessionGuard` (cookie `uo_session`, `@Public()` to skip) → `CsrfGuard` (Origin check plus `X-CSRF-Token` header vs. the session's token; `@SkipCsrf()` only for HMAC-signed webhooks) → `CapabilityGuard`. The web client (`apps/web/src/lib/api.ts`) reads `uo_csrf` and sends the header.
- **Stage gates**: `stageGateIssues(facts, target)` in `packages/shared/src/rules.ts` is the only place stage requirements are defined; `gateIssueArea` beside it maps each message to the tab that fixes it (the web links blocked moves there), so keep the two in step. They're cumulative and the early stages have none. The API builds facts with `loadGateFacts` (`opportunities/facts.ts`), which reduces restricted data to presence flags. Moving to `live_won` only happens via `OpportunitiesService.activate`; won deals can't change stage and can't be unassigned; "lost" is `outcome`, not a stage.
- **Never delete or overwrite history.** DB triggers make `audit_logs` and `timeline_entries` append-only and forbid deleting or deactivating `opportunities`. The one exception is `OpportunitiesService.purgeLeads` (administrators, `opportunity.purge`): it deletes leads at New Lead that nobody worked on (see `purgeable`) with `uo.allow_purge` set for its transaction, the same flag the retention purge uses, and writes one audit entry. Live and ended `energy_contracts` and live `merchant_applications` are read-only in services. `form_signatures` and `bill_checks` are append-only and `generated_forms` can't be deleted (triggers). Renewals create new rows linked by `previous_*_id`. Uploads are new `document_versions`. Corrections to the timeline are new entries with `correctsId`.
- **Every mutation records itself**: `AuditService.record/log/timeline`, passed the transaction (`tx`) so it commits atomically. Never put restricted values (DOB, nationality, address, IBAN, compliance notes) in timeline bodies or audit `data`; `redact()` strips known keys as a backstop.
- **Sign-in paths share `AuthService.issueSession` / `checkTotp`.** Password login and SSO (`auth/sso.service.ts`: OIDC code + PKCE, flow state in an HMAC-signed `uo_sso` cookie, ID token verified with node:crypto against the provider JWKS) must both go through them. SSO never creates users. Tests use `test/support/mock-oidc.ts`.
- **Live updates** go through `RealtimeService.publish(userIds, event)` (`src/realtime/realtime.ts`, Redis pub/sub → SSE at `/api/realtime/stream`). Events carry ids and short previews only, never restricted data; the web `RealtimeProvider` just invalidates TanStack queries. Tests override `REALTIME_BUS` with `LocalRealtimeBus` (inspect `.published`).
- **Chat access** is computed, not stored, and chat is off unless `CHAT_ENABLED` is set (`ChatEnabledGuard` 404s every chat route; `/auth/me` returns `features.chat` and the web hides chat). Integration tests switch it on in `test/support/app.ts`. Access rules: DMs and private channels need membership, public channels are open, deal discussions follow `canReadOpportunity` (`ChatService.canSee`). **Calls** dial only numbers returned by `CallsService.numbers`, and `finalise` writes the timeline once (guarded by `loggedAt`). RingCentral is behind `TelephonyProvider`; tests use `test/support/mock-ringcentral.ts`.
- **Encryption**: restricted columns end in `Enc` and go through `CryptoService` (AES-256-GCM, `v1:<keyId>:…`, previous key accepted for rotation). Principals also store `hasDob`/`hasNationality` so rules don't decrypt. Reads unmask only with the capability, and call `audit.sensitiveAccess`.
- **Supplier forms** (`src/forms/`): `FormTemplate` stores the PDF and positioned fields (`formFieldSchema`, PDF points from the bottom-left; `comb` for character boxes). `pdf.ts` fills with pdf-lib, strips all AcroForm widgets, then `verifyPdf` re-opens the saved bytes and checks every drawn hex string and signature image is in the page content; any issue sets `qcPassed=false`, which blocks signing and the `submitted` gate. `GeneratedForm` keeps a field snapshot and encrypted values; regenerating supersedes. Uploaded signatures (`FormSignature`, append-only) need a reviewer other than the uploader; so does a scan of a form signed on paper (`uploadSignedCopy`, recorded in `signedCopyUploadedById`). Field sources live in `FORM_SOURCES` (shared); `bank.*` are restricted. Change of supplier requires a passed `BillCheck` on the latest energy-bill version. The web editor renders pages with pdf.js (`components/forms/pdf-page.tsx`).
- **Supplier applications** (`src/supplier-applications/`, `packages/shared/src/{supplier-applications,flogas,bord-gais}.ts`, `docs/flogas-electricity.md`, `docs/bord-gais-electricity.md`): a supplier's own form with a dedicated UI, shown while it applies (`supplierApplicationApplies`: Electricity + Flogas, or Electricity + Bord Gáis Energy, old spellings matched by `isBordGaisSupplier`). Saving writes each value to its CRM record; `SupplierApplication.answers` holds only supplier-only answers. Each supplier's PDF mapping lives only in its `layout.ts`: Flogas draws on the page (`pdf.ts`), Bord Gáis fills the PDF's own AcroForm fields by name (`forms/acroform.ts`: regenerates appearances, verifies values and appearances after reopening, flattens the signed copy; fields carry `pdfField`). Templates are `FormTemplate`s with `workflow` set (recognised by SHA-256, hidden from the generic filler, fields locked). `ApplicationDocuments` is shared: generating stores an append-only `SupplierApplicationVersion` (encrypted data snapshot + hash) through `FormsService.storeGenerated`, and signing links for these forms are only created through the application (`SigningService.createLink(..., { viaApplication })`), which refuses a version the CRM has moved on from. Visual checks: `npm run flogas:fixture` / `npm run bord-gais:fixture -w @uo/api -- <pdf> <out>`; set `BORD_GAIS_PDF` to check the test stand-in against the real form.
- **One interface, back-office handover** (`packages/shared/src/handover.ts`): every role uses the same web UI; the sidebar (`components/shell.tsx` `NAV`), Home (the work queue for `opportunity.submit`) and opportunity tabs are filtered by capabilities only, never by role. A deal is handed over at `HANDOVER_STAGE` (supplier_selected, `isHandedOver`), which creates the `back_office_handover` task in `onStageEntered`; `/cases?scope=back_office` is the work queue. The API keeps enforcing capabilities.
- **Workflow cases** (`src/workflows/`, `packages/shared/src/workflows.ts`): every energy deal follows a case kind (`caseKind`: change of entity > change of supplier > renewal > new supply). Status and steps are derived by `caseSteps` from evidence, never stored. Evidence tables are append-only (`submissions`, `submission_responses`, `lease_checks`, `terms_checks`, `supply_occupancies`; `workflow_cases` can't be deleted). Gates in `stageGateIssues` read `GateFacts.workflow` (presence flags from `loadGateFacts`; pass `CryptoService` for the incoming/outgoing IBAN comparison). Activation uses the `live_won` gate: energy deals need a recorded submission and acceptance. A change of entity fills forms only from the incoming customer; `outgoing.*` sources are separate.
- **Automations must be idempotent.** Use `ActivitiesService.ensureAutomated` with an `automationKey` (a partial unique index allows one *open* row per opportunity and key) and `completeAutomated` to close it. Renewals rely on the unique `renewal_source_key`; outbound integrations on `integration_jobs.idempotency_key`; webhooks on `(provider, event_id)`. Background handlers live in `automations/` and are wired to BullMQ in `jobs/workers.ts`; enqueue through the `JOB_QUEUE` abstraction, never `bullmq` directly. `BullJobQueue` turns `:` in job ids into `-` (BullMQ rejects colons); tests use `RecordingJobQueue`, which never talks to Redis.
- **Vendor integrations are adapters chosen by env** (`modules.ts`): `ObjectStorage` (S3/local with signed links), `VirusScanner`, `OcrProvider`, `SignatureProvider`, email/WhatsApp senders, `SubmissionChannel`, `DocumentReader` (`src/ai/`: Claude via `@anthropic-ai/sdk`, on when `ANTHROPIC_API_KEY` is set; "Read bill" and business cards return suggestions only, a person ticks what is saved; tests override `DOCUMENT_READER`). Unconfigured adapters fail with `NotConfigured` (the job is dead-lettered), never with fake success.
- **Errors**: throw `RuleViolation(issues[])` for business rules (422, `issues` are user-facing sentences), plus `Forbidden`/`NotFound`/`Conflict`; `HttpErrorFilter` maps them. Bodies and queries are validated with `new ZodPipe(sharedSchema)`. Prisma Decimals are turned into numbers by a global interceptor in `bootstrap.ts`.
- **Dates**: calendar dates are `YYYY-MM-DD` strings in shared/web, and `@db.Date` (UTC midnight) in Prisma; convert with `dateOnly`/`isoDay` (`common/values.ts`). Business "today" is Europe/Dublin (`today()` in shared).
- **NestJS DI needs value imports**: ESLint's `consistent-type-imports` is off for `apps/api` because constructor-injected classes must not be `import type`.
- **Responsive rules** (enforced by `apps/web/e2e/responsive.spec.ts` at 320/375/768/1024/1280/1920px): no page-level horizontal scroll; wide tables live in an `overflow-x-auto` wrapper with `tabIndex={0}`, and lists people use on phones (opportunities, customers) render as cards below `md`; grid and flex children that hold tables need `min-w-0` (`Card` has it); text ≥ 12px (no `text-[10px]`/`text-[11px]`); touch targets ≥ 24px; hover-only controls must also show where there's no hover (`[@media(hover:hover)]:opacity-0`). Screenshots and a report land in `apps/web/e2e-report/responsive/`.
- **Next.js page files** may only export the page component; put shared constants in `src/lib` or `src/components`.
- **The team guide** (menu: Help & guide, `/help`) is `apps/api/assets/crm-guide.html`, a self-contained page with its screenshots embedded, served to signed-in users by `GET /api/help/guide` with its own strict CSP (no external loads) and framed by the web app. Replace the file to update it.

## Product rules to preserve

Opportunities are permanent (apart from the administrators' purge of untouched leads). The master sheet migration (`src/migration/`, `packages/shared/src/migration.ts`) is the only other path that writes won deals without the stage gates; it is keyed by `importKey` and audited as `migration.import`. Creating or linking a customer must not change an opportunity's stage, outcome, owner or active flag. Duplicate customers are flagged (email, phone, CRO, VAT, name and postcode) and never merged automatically (merge is `customer.merge`, managers only). Irish formats: MPRN is 11 digits starting "10", GPRN is 7 digits; exceptions need `formatExceptionReason`. Phone matching normalises +353/+44 and the trunk 0 (`phoneKey`).
